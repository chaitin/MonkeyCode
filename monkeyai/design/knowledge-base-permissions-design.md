# 知识库权限产品方案

> 更新日期：2026-11-13。状态：权限功能已开发并通过集成验证，尚未发布。
>
> 本文记录产品目标、操作流程、权限规则、异常体验、验收标准，以及对应的表结构与 migration 调整。不包含接口、业务代码实现、框架选型或技术测试方案。

## 1. 产品目标

让知识库从“所有者维护、其他人查看”扩展为可控的多人维护。

核心要求：

1. 授权分两级：定位人或组，在该对象行右侧直接选择只读或读写。
2. 一个“人或组 + 权限”是一条独立授权记录，可以单独修改、移除。
3. 权限分为只读、读写两档；读写包含只读的全部能力。
4. 管理员可以授予普通成员在客户端维护系统知识库的权限，不必把成员设为后台管理员。
5. 读写权限包含新增、编辑、整理和删除文档及文件夹，支持批量删除内容。
6. 内容管理与知识库管理分开：读写不包含修改授权、修改知识库设置或删除整个知识库。

## 2. 概念与边界

| 概念 | 产品含义 |
| --- | --- |
| 系统知识库 | 由管理员创建和管理，供组织成员使用；成员按授权维护内容 |
| 个人知识库 | 归个人所有，由所有者决定分享给谁及分享权限 |
| 授权对象 | 一个用户、一个分组，或系统知识库中的全体成员 |
| 只读 | 查看、搜索和使用知识库内容 |
| 读写 | 包含只读；新增、编辑、整理和删除文档及文件夹，支持批量删除内容 |
| 知识库负责人 | 系统库的管理端管理员，或个人库所有者；负责授权、设置和整库删除 |

两档权限均作用于整个知识库。库内文档、文件夹和分片继承知识库权限，不单独授权。

同一成员对不同知识库可以拥有不同权限。拥有某个库的读写权限，不会获得其他库的权限。

读写是知识库内容权限，不是后台管理员权限。

## 3. 权限矩阵

以下操作以成员账号有效、知识库启用且成员具备相应使用资格为前提。

| 操作 | 只读 | 读写 |
| --- | --- | --- |
| 查看知识库、目录、文档正文 | 可以 | 可以 |
| 查看分片、学习状态及处理结果 | 可以 | 可以 |
| 搜索、提问、引用知识内容 | 可以 | 可以 |
| 新增文档、使用已有导入能力添加内容 | 不可以 | 可以 |
| 新建文件夹 | 不可以 | 可以 |
| 编辑正文、修改文档或文件夹名称 | 不可以 | 可以 |
| 同库移动文档或文件夹、调整排序 | 不可以 | 可以 |
| 重新学习文档、重试失败任务 | 不可以 | 可以 |
| 删除文档 | 不可以 | 可以 |
| 删除文件夹及其中的内容 | 不可以 | 可以 |
| 批量删除内容 | 不可以 | 可以 |
| 修改成员授权、再次分享 | 不可以 | 不可以 |
| 修改知识库名称、说明、标签、启停 | 不可以 | 不可以 |
| 删除整个知识库 | 不可以 | 不可以 |
| 调整全库索引及模型设置 | 不可以 | 不可以 |

最后四类操作由知识库负责人按已有管理能力执行。个人库所有者不因本方案自动获得原本没有开放的系统维护功能。

补充说明：

- 读写成员能够维护和删除该库中其他成员创建的文档，不限于本人创建的内容。
- 只读成员即使是文档创建者，也不能修改或删除文档；操作能力取决于当前知识库权限。
- 正文编辑和文档删除都可能导致内容丢失，建议分别通过历史版本和回收站提供恢复能力；权限本身不等于内容备份。
- 本期移动限定在同一个知识库内，不包含跨知识库迁移内容。
- 不因本方案新增文件格式解析能力，导入范围以产品已提供的能力为准。

## 4. 管理端：对象行内授权

### 4.1 入口

系统知识库详情提供“权限管理”入口。

页面在知识库表单中提供授权选择器，打开后展示人和组及其当前权限。

说明文案：

> 选择成员或分组，并设置只读或读写权限。被授权成员可以在客户端使用或维护该知识库。

个人知识库在管理端保持只读，不提供修改个人库授权的入口。

### 4.2 选择对象和权限

打开授权选择器，支持按姓名、邮箱、拼音搜索成员或分组。在每个人或组的右侧直接选择“只读”或“读写”，替代原来的勾选框；不再使用“下一步”或单独的权限选择页面。

- 未授权对象显示“未授权”，不默认创建授权。
- 选择权限后，该人或组形成一条独立授权记录。
- 已授权对象显示当前权限，可直接切换；选择“未授权”移除该条直接授权。
- 组授权只保存一条记录，不展开为成员逐条授权。
- 系统库支持全体成员授权。
- 同次操作可以为不同人或组选择不同权限。
- 不展示流程说明、继承规则等辅助提示，保留搜索、对象名称和权限操作。

### 4.3 保存结果

点击知识库表单的保存按钮后统一生效；取消表单不保存修改。任意对象失效或保存失败时保留当前选择，不显示部分保存成功。

例如张三选择只读、产品组选择读写，保存两条独立授权记录。组授权的继承和多来源取最高权限规则不变。

## 5. 修改、移除与有效权限

### 5.1 修改一条授权

点击某行“修改权限”，选择新的权限并保存，只影响这一条记录。

只读升级为读写后，该对象获得新增、编辑、整理和删除内容的能力；读写降为只读后，失去来自该记录的全部内容写入能力。最终权限仍需合并其他授权来源。

列表必须展示保存后的实际权限。操作失败保留原状态，不能先显示成功再让用户误以为已生效。

### 5.2 移除一条授权

点击“移除”，确认后取消该对象的这条直接授权。

提示文案：

> 移除此授权后，该成员可能仍通过分组或全体成员授权访问知识库。

移除授权不删除该成员已创建的文档，也不改变文档归属。文档仍保留在原知识库中。

### 5.3 多条来源取最高权限

同一个人可能同时获得个人、分组和全员授权。最终权限取最高档：

**无权限 < 只读 < 读写。**

| 授权来源 | 最终结果 |
| --- | --- |
| 产品组只读 + 张三个人读写 | 张三读写 |
| 产品组读写 + 张三个人只读 | 张三仍读写 |
| 全体成员只读 + 产品组读写 | 产品组成员读写，其他成员只读 |

个人只读不构成对组权限的限制。要降低一个人的有效权限，必须调整其全部高权限来源。

第一版不提供“禁止访问”或“个人授权覆盖组授权”等例外规则。

### 5.4 查看权限来源

知识库负责人可以搜索成员，查看其最终权限及来源，例如：

> 张三当前读写。来源：产品组读写；另有个人只读授权。

普通成员只需看到自己的最终权限，不展示完整的其他成员授权名单。

## 6. 分组及全员规则

- 分组授权包含该组和下级分组成员。
- 新加入分组的人自动获得对应权限，退出后失去该来源的权限。
- 一条分组授权始终显示为一条记录，不展开为每个成员的个人授权。
- 分组被删除后，该来源不再赋予权限；其他有效来源仍然保留。
- 全体成员授权覆盖当前及未来符合条件的有效成员。
- 停用或删除的成员不能继续使用知识库，不因仍在某分组中而例外。
- 同一个人通过多个分组重复获得权限时，只计算最终最高权限，不在授权列表自动生成重复个人记录。

## 7. 客户端维护系统知识库

### 7.1 成员不需要成为管理员

管理员在管理端给普通成员授权后，成员直接在客户端使用对应能力。

成员修改的是原系统知识库，其他有权访问的成员能够看到修改结果；不会复制为个人知识库，也不会改变系统库所有权。

后台管理员身份与客户端内容权限分开。管理员如果使用普通客户端维护系统库，也按该库授予的内容权限操作。

### 7.2 列表与详情展示

知识库展示两个独立标识：

- 归属：系统知识库、个人知识库。
- 我的权限：只读、读写；本人个人库可显示“所有者”。

示例：“产品资料库 · 系统知识库 · 读写”。

### 7.3 操作入口

- 只读成员：查看、搜索、引用，无编辑及删除入口。
- 读写成员：增加新建、导入、编辑、重命名、移动、排序、重新学习、单项删除、批量删除和文件夹删除入口。
- 成员无论获得哪档内容权限，都不会因此看到系统库的授权、整库删除和管理设置入口。

通过助手操作知识库时，遵循同样的权限：只读不能要求助手修改或删除内容；读写可以新增、编辑和删除内容，但不能要求助手转授权或删除整个知识库。

## 8. 个人知识库分享

个人库所有者使用相同的行内交互，在人或组右侧选择只读或读写。

接收者按照相应权限维护原个人库，不获得所有权，也不能再次分享、改变授权或删除整个库。

个人库新分享默认不提供“全体成员”选项。若历史存在全员分享，继续展示原范围，允许所有者调整权限或移除，不在产品升级时悄悄取消已有分享。

所有者保留知识库管理能力。管理端对个人库仍只读，不因为本方案获得个人库内容写入或授权修改能力。

## 9. 删除体验

### 9.1 单文档删除

只有读写成员和知识库负责人可以删除。确认界面展示文档名称及删除后不再用于检索、提问和引用的影响。

### 9.2 文件夹删除

删除确认明确提示包含多少子文件夹和文档，说明会一并删除其内容，不能只显示“删除文件夹”而隐藏影响范围。

### 9.3 批量删除

展示选中项及实际受影响的内容数量。父文件夹和子项同时选中时，按实际影响范围去重，避免重复统计。

没有删除权限时不展示批量删除入口。确认过程中权限变化时停止操作并说明原因。

### 9.4 配套建议：回收站

回收站属于建议配套能力，不因开放读写授权就视为已经实现。若纳入本期，采用以下产品规则：

- 删除的内容进入知识库回收站，保留 30 天；期间不出现在正常目录和检索结果中。
- 读写成员和负责人可查看、恢复删除内容。
- 提前永久删除和清空回收站仅负责人可执行。
- 文件夹按整批恢复其原有子树；原父目录不存在时恢复到知识库根目录并提示。
- 到期自动清理；整库删除不由文档回收站提供恢复保证。

如果本期不包含回收站，删除确认必须明确标注“删除后无法恢复”，不能出现“可在回收站找回”等误导文案。

## 10. 权限变化和异常体验

| 场景 | 产品行为 |
| --- | --- |
| 升级权限 | 再次进入或刷新后展示新增能力 |
| 读写降为只读 | 新增、编辑、移动和删除入口消失，已打开的写入操作也不能继续完成 |
| 编辑过程中降为只读 | 保存被拒绝，提示权限变化，保留未提交草稿供复制 |
| 完全失去访问权限 | 后续不能读取或操作，知识库从可访问列表移除 |
| 知识库停用 | 普通成员暂停使用，包括读写成员；负责人可在管理入口维护和恢复启用 |
| 两人同时修改授权 | 后提交者获知列表已变化，刷新确认后重试，不自动覆盖对方修改 |
| 待授权成员失效 | 指明失效对象，保留其他选择，修正后重新保存 |
| 成员退出授权分组 | 后续操作使用新的有效权限；其他来源仍有效 |

权限变更不能撤销已完成的内容修改，也不能收回成员此前已经读取、复制或用于历史对话的内容。

已接受的文档修改，其学习处理可以继续完成；撤销作者权限不删除这份已提交内容。被删除文档不再作为可用知识提供，不能因处理任务完成而重新出现。

## 11. 协作维护的配套体验

### 11.1 修改人及修改时间

文档展示最近一次内容修改人及时间，方便追踪维护者。学习状态变化不应被展示为某个人重新编辑了正文。

### 11.2 编辑冲突

两人同时编辑同一文档时，后提交者获知内容已更新，保留本地草稿，查看最新内容后再决定如何合并。不能无提示覆盖他人修改。

### 11.3 建议配套：文档历史版本

若纳入本期，保存正文后保留历史版本；可读取者可查看仍保留的历史正文，读写成员可将历史版本恢复为新的当前版本。恢复不会删除中间版本。

历史版本仍继承当前知识库权限，失去读权限后不能继续查看。永久删除历史版本仅负责人可操作。

历史版本保留时长、数量及容量限制需要在该配套能力正式立项时确定；不能把尚未实现的历史版本作为当前防丢失承诺。

### 11.4 操作与授权记录

负责人可以查看谁在什么时间新增、修改、移动、删除了哪些内容，以及谁给哪个对象调整了什么权限。

普通成员不因此获得完整授权名单。操作记录不等同于正文历史版本，不能仅凭操作记录承诺恢复内容。

## 12. 表结构调整记录

本节记录产品方案涉及的数据结构变化，并在 12.8 节明确 migration 修改范围。对应 migration 文件已新增；目标环境数据库需随发布执行迁移。

### 12.1 授权表 resource_access_grants：必需调整

复用现有授权表，不新建一套知识库权限表。

| 项目 | 当前情况 | 设计调整 |
| --- | --- | --- |
| access_level | 已支持 read_only、read_write | 直接复用，分别对应只读、读写；read_write 包含内容删除 |
| 权限取值约束 | 已允许 read_only、read_write | 保持不变，不增加第三种权限值；其他资源原有权限含义不变 |
| 授权主体 | user_id、group_id、all_users | 复用；每条记录只能指定其中一种主体 |
| 主体唯一性 | 已有同资源用户、分组、全员唯一约束 | 保留；同库同主体只有一条记录，唯一性不包含权限值 |
| id | 已有授权记录标识 | 逐行修改权限时保留，不因为修改权限生成另一条记录 |
| created_at / updated_at | 已有时间字段 | 创建时间保留，权限调整更新修改时间 |
| granted_by_user_id | 已有授权操作者字段 | 保留初次授权者含义，不重新解释历史值 |
| updated_by_user_id | 当前无独立最后修改人字段 | 新增 uuid、可空，记录最近一次授权调整者；历史未知时为空 |
| usage_requirement | 已有字段 | 知识库仍为 optional，不作为额外权限档位或启用开关 |

权限存储值：

| 产品名称 | 存储值 | 含义 |
| --- | --- | --- |
| 只读 | read_only | 读取和使用内容 |
| 读写 | read_write | 读取、创建、编辑、整理和删除文档及文件夹 |

一条记录示例：知识库 A + 张三 + read_write。选中两个人和一个组后，保存三条记录。用户与分组授权可以同时存在，按产品规则合并最高权限。

历史只读授权保持只读，不自动升级。历史上存在但未实际赋予知识库写能力的其他权限记录，需要逐项确认，不直接让旧值获得新的操作能力。

### 12.2 knowledge_bases：复用现有版本

| 字段 | 类型 | 设计 |
| --- | --- | --- |
| revision | integer | 复用现有字段；授权发生有效变更时更新版本，用于识别多人修改冲突；不新增字段或约束 |

授权列表使用知识库当前版本。保存时若版本已变化，提示刷新并重新确认，不覆盖其他人的修改。

该版本由知识库信息和授权共同使用，因此名称、说明等其他知识库信息更新，也可能触发授权编辑冲突。界面应提示“知识库信息或权限已更新，请刷新后重试”，不能一律声称有人修改了权限。

不新增独立授权版本字段或对应的正整数检查约束，沿用现有 revision 及其约束。已有 ownership_type、owner_user_id、enabled 保持原意，授予内容管理权限不改变所有权或启用状态。

### 12.3 knowledge_base_documents：最近内容修改人

| 字段 | 类型 | 设计 |
| --- | --- | --- |
| updated_by_user_id | uuid | 新增、可空，最近一次内容或目录结构修改者；历史无法确认时不伪造 |
| content_updated_at | timestamptz | 新增、可空，最近一次用户内容或结构修改时间，与学习状态更新区别展示 |
| revision | integer | 复用现有版本字段，用于表示文档版本，不再新建同义字段 |

created_by_user_id 继续记录原创建者；其他人参与编辑不能覆盖它。

### 12.4 内容和授权变更记录

复用现有业务审计记录，记录操作者、知识库、目标对象、动作、时间及变更前后权限。当前设计不要求另建一张权限操作日志表。

删除授权后，历史授权变更仍需可查看，不依赖已删除授权行才能解释记录。正文版本快照不放在普通操作记录中。

### 12.5 若纳入回收站：删除记录结构

以下结构仅在回收站确定纳入范围时新增；两档权限本身不要求这些字段。

新增 `knowledge_base_deletion_batches`，保存一次删除的归属及恢复信息：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| id | uuid | 删除批次标识 |
| knowledge_base_id | uuid | 所属知识库 |
| deleted_by_user_id | uuid，可空 | 执行删除的人 |
| deleted_at | timestamptz | 删除时间 |
| expires_at | timestamptz | 到期永久清理时间 |
| restored_by_user_id | uuid，可空 | 执行恢复的人 |
| restored_at | timestamptz，可空 | 恢复时间 |

`knowledge_base_documents` 增加：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| deleted_at | timestamptz，可空 | 是否处于回收站 |
| deletion_batch_id | uuid，可空 | 所属删除批次，文件夹及其本次删除的后代关联同一批次 |

恢复整个删除批次，不复活早于该批次已独立删除的文档。原父目录不存在时恢复到根目录。产品要求能按知识库和删除时间浏览回收站、按到期时间清理，结构应支持这两类查找。

文档分片不增加独立授权。回收站中的文档及其分片不参与正常阅读和检索；恢复后根据需要重新学习。任务表本方案不增加权限角色字段。

### 12.6 若纳入历史版本：正文版本结构

新增 `knowledge_base_document_versions`，仅在历史版本功能确定纳入时使用。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| id | uuid | 历史版本标识 |
| knowledge_base_id | uuid | 所属知识库 |
| document_id | uuid | 所属文档 |
| revision | integer | 对应文档版本号，与 document_id 组合唯一 |
| title | text | 当时的文档标题 |
| content | text | 当时的正文快照 |
| changed_by_user_id | uuid，可空 | 修改者，历史未知时允许为空 |
| created_at | timestamptz | 版本产生时间 |
| restored_from_revision | integer，可空 | 本次保存若来自恢复，记录来源版本 |

该表记录文档正文历史，不作为文件夹历史或整库备份。原始文件的版本化存储不在本次权限范围内。永久删除文档时，其正文历史同步按删除规则处理。

### 12.7 结构范围汇总

| 范围 | 表结构变化 |
| --- | --- |
| 两档授权 | 复用 resource_access_grants 既有权限值及约束；增加最后修改人 |
| 授权修改冲突提示 | 复用 knowledge_bases.revision，无表结构变化 |
| 内容修改人展示 | knowledge_base_documents 增加内容修改人和时间 |
| 操作记录 | 复用已有业务审计结构，不新建权限日志表 |
| 回收站，建议配套 | 删除批次表 + 文档删除标记及批次关联 |
| 历史版本，建议配套 | 新增文档正文版本表 |

### 12.8 Migration 修改说明

#### 12.8.1 文件与范围

本次权限功能在 `000039_create_kb_tables` 基础上采用增量迁移，已新增：

- `backend/migrations/000040_kb_permissions.up.sql`
- `backend/migrations/000040_kb_permissions.down.sql`

本次已核对使用编号 000040；后续迁移继续使用下一可用编号。

此前三张知识库表全拼命名已修改原 000039，本次不再重复改名，也不通过执行 000039 的 down/up 重建知识库。已执行到版本 39 的数据库需要实际执行这次新增字段的迁移；仅修改旧建表文件不会更新已有数据库。

新安装环境按顺序执行原有迁移和本次增量迁移，最终得到相同结构，不需要另外维护一套新安装专用建表定义。

本次 000040 只包含两档权限及必需配套字段。回收站、历史版本仍为可选能力，确认纳入后各用独立的后续 migration，不混入 000040。

#### 12.8.2 Up 必须完成的结构修改

| 表 | 修改内容 | 存量数据处理 |
| --- | --- | --- |
| resource_access_grants | 新增 `updated_by_user_id uuid NULL` | 既有记录保持 NULL，不用初次授权者冒充最后修改者 |
| knowledge_base_documents | 新增 `updated_by_user_id uuid NULL` | 既有记录保持 NULL，不猜测内容修改人 |
| knowledge_base_documents | 新增 `content_updated_at timestamptz NULL` | 既有记录保持 NULL，不把学习状态更新时间误当正文修改时间 |

新增的操作者字段用于展示历史归属，不增加级联删除行为；成员被删除不应导致授权记录或文档随之删除。以上字段不单独新增索引。

以下结构明确不改：

- `access_level` 保留现有 `read_only`、`read_write` 两个值，不增加 `manage`。
- 原权限取值约束、主体互斥约束及用户/分组/全员唯一索引保持不变。
- 不新增权限表，不新增与 access_level 重复的 role 或 permission 字段。
- 不修改知识库所有者、启用状态、文档创建者和已有文档 revision。
- knowledge_bases 复用现有 revision 及其约束，不增加独立授权版本字段，不重置已有版本值。
- 不修改分片表和学习任务表，不因权限功能重建向量或文档内容。

#### 12.8.3 存量授权处理

本次结构迁移不批量修改 access_level，不自动把任何只读授权升级为读写，也不通过删除后重建授权来补字段。

迁移前盘点知识库授权：

1. 既有 read_only 保持只读，授权记录标识和主体不变。
2. 若发现历史 read_write，须核实其原始授权意图。旧功能没有据此开放知识库协作写入，不能仅凭历史字段值就自动激活新增写入和删除能力。
3. 未确认的历史 read_write 是功能开放前的待处理项，先保留授权快照，再由负责人明确保留读写或调整为只读；不得在 migration 中静默决定。
4. 非知识库资源的授权值及权限含义全部保持不变。

结构迁移完成不代表存量异常授权已核实。只有授权核对完成后，才能开放相应知识库的协作写入。

#### 12.8.4 迁移版本管理

沿用项目现有的 golang-migrate 和 `schema_migrations` 管理版本，不再要求额外创建 migrations 表或维护 migrations.name 记录。

- 本次增量迁移由现有工具按版本顺序执行，已完成版本不重复执行。
- 本次结构修改应整体成功或整体回退，不能留下部分字段更新却视为完成的状态。
- 执行失败后先核对实际结构及工具记录的 dirty 状态，修复后按现有迁移流程恢复；不能直接把失败版本标记为成功。
- 不手工删除或改写迁移版本记录来强制重复执行旧建表文件。

#### 12.8.5 Down 与数据影响

普通应用回退优先保留新增字段，不要求同时执行数据库 down。确需退回本次结构时，先确认已无功能使用新增字段，并保存新增元数据。

本次 down 只回退本次引入的内容：

1. 删除 knowledge_base_documents.updated_by_user_id、content_updated_at。
2. 删除 resource_access_grants.updated_by_user_id。

knowledge_bases 的现有 revision 字段、版本值及其约束全部保留，不属于本次回退范围。

版本回退由现有迁移工具管理，不手工修改 schema_migrations。已有环境中的其他迁移辅助表和历史记录不属于本次清理范围；不删除知识库、文档、分片、任务或授权，不批量改写 read_write。

执行 down 会丢失新增的最后修改人和内容修改时间；再次 up 只恢复可空字段，不能自动还原这些元数据。正文和既有授权必须保持不变。

#### 12.8.6 可选能力的独立迁移

| 可选能力 | 后续独立 migration 的结构范围 | 回退限制 |
| --- | --- | --- |
| 回收站 | 新增 knowledge_base_deletion_batches；给文档增加 deleted_at、deletion_batch_id；支持按知识库删除时间、批次和到期时间查找 | 有未处理回收站内容时不得直接删除标记，否则内容可能意外重新出现；先明确恢复或永久清理，再回退结构 |
| 历史版本 | 新增 knowledge_base_document_versions；增加 document_id + revision 唯一约束 | 删除版本表会丢失历史正文，必须先保存历史数据；当前正文不应随之删除 |

这些后续 migration 沿用项目现有文件命名和版本管理方式，由 golang-migrate 统一管理。未确认纳入的能力不提前建表。

## 13. 产品验收标准

| 场景 | 预期结果 |
| --- | --- |
| 选择两个人和一个组，选择读写 | 产生三条独立授权记录 |
| 修改其中一个人的权限 | 只改变该行，其余授权不变 |
| 重复添加同一对象 | 提示已授权，不产生重复行 |
| 普通成员获得系统库读写 | 可在客户端新增、编辑、移动和删除文档及文件夹 |
| 只读成员删除本人创建的文档 | 不允许，创建者身份不绕过权限 |
| 读写成员删除其他人创建的同库文档 | 允许，权限作用于整个知识库 |
| 读写成员修改授权或删除整个库 | 不允许 |
| 组读写、个人只读 | 最终读写，能解释权限来源 |
| 移除个人读写，仍有组只读 | 成员降为只读，内容保留 |
| 成员加入或退出授权组 | 后续使用获得或失去该来源权限 |
| 个人库所有者授予他人读写 | 接收者读写内容，不能转授权或删除整个库 |
| 正在编辑时失去写权限 | 无法保存，保留未提交草稿并提示 |
| 两人同时编辑同一文档 | 提示内容冲突，不静默覆盖 |
| 知识库停用 | 普通成员不能继续读取或维护 |
| 通过助手要求执行操作 | 与本人在客户端的权限一致 |
| 删除包含子内容的文件夹 | 删除前明确展示影响范围 |
| 本期未提供回收站 | 明确提示删除不可恢复 |
| 纳入回收站后删除与恢复 | 内容按期限保留，读写成员能恢复，不能提前永久清除 |

核心验收路径：管理员选择一个普通成员 → 授予系统库读写 → 成员在客户端新增、编辑、整理和删除文档及文件夹 → 始终不能修改授权或删除整个库 → 降为只读且无其他读写来源后，只能查看和使用内容。
