# Firecracker 云环境与宿主安装器完整设计

状态：已开始分阶段实施，当前仅完成平台探测与安全选型基础，完整驱动、安装器和真实部署尚未交付，进展见[实施记录](firecracker-environment-implementation.md)。本文汇总已确认产品决策，并给出工程设计；标为“建议／待确认”的参数和政策不视为用户已批准。用户已授权开始代码实施，但未授权安装真实宿主、修改启动参数、迁移用户环境或启用真实计费。

决策来源：[执行引擎扩展与环境计费讨论](environment-engines-billing-discussion.md)。现有控制面见[环境控制](environment-control.md)，接口基线见[客户端接口](environment-client-api.md)。旧文档中的 containerd 方案、资源预留和只读系统目录等历史描述，不覆盖当前 Docker/gVisor 代码或本文明确的新设计。

## 1. 目标与已确认决策

目标：在保留现有 gVisor 能力的前提下，增加具有独立 Linux 内核、可持久安装软件的 Firecracker 开发环境，并交付自动选型的宿主安装器。

| 项目 | 已确认决策 |
| --- | --- |
| 执行方式 | gVisor 与 Firecracker 并存；每个环境创建后固定驱动，不静默互换 |
| 安装入口 | 同一条宿主接入命令自动检测；首次安装优先 Firecracker，不满足条件时选择验证通过的 gVisor |
| 镜像复用 | 继续使用平台维护的 Dockerfile 和 Docker／OCI 镜像；不以虚拟机内套 Docker 容器作为基础执行方案 |
| 转换位置 | 每台 Runner 首次使用匹配镜像时本地转换并缓存；不在发布阶段预生成开发环境系统盘 |
| 磁盘 | 每环境一块独立可写盘，系统和用户数据共用总容量；稀疏 raw 文件＋ext4；支持时 reflink，否则稀疏复制 |
| 持久化 | 停止／启动复用原磁盘，保留系统修改、软件、项目、用户目录与 runtime 状态 |
| 权限 | Firecracker 中普通用户运行 runtime，允许用户 sudo；gVisor 保持现有非特权约束 |
| 管理 | Firecracker API 管理虚拟机，vsock 连接虚拟机内的小型管理服务；不新增 SSH 管理通道 |
| 分发 | 中心服务统一分发固定版本组件；Runner 不从公网临时编译或安装运行依赖 |
| 磁盘超卖 | 允许逻辑容量超卖，同时检查真实空间；危险区允许 Runner 自动暂停／停止相关环境 |
| 数据销毁 | 停止保留两块盘；删除环境后磁盘转为保留数据；永久销毁单独确认，不自动到期删除 |
| 首版范围 | 冷启动；不做内存快照、跨 Runner 自动迁移或失联自动替代实例；不预装 Docker |
| 计费 | 同规格同价、按确认运行时间计费、存储暂不收费；平台磁盘保护暂停期间不收费 |

首版不承诺任意 OCI 镜像可启动、Docker／Compose 完整兼容、所有磁盘同时写满、磁盘持久化即备份、零停机或零数据丢失。Kubernetes 供应后端和其他虚拟化后端不纳入本方案。

阅读导航：第 1～3 节为决策与架构；第 4～8 节为安装、分发、转换和磁盘；第 9～14 节为保护、控制、安全与计费；第 15～20 节为故障、交付、验收和待定项。

## 2. 名词与职责

为避免“客体”等术语造成混淆，本文统一写“虚拟机内”。

| 名称 | 职责／含义 |
| --- | --- |
| 中心服务 | 授权、规格与调度、目标状态、设备授权、连接、计费和组件分发 |
| Runner | 部署在承载开发环境的 Linux 服务器上的管理程序；现有程序名为 `monkeyai-engine` |
| 宿主服务器 | 运行 Runner 和开发环境的物理机或具备所需能力的云服务器，不等同于 Runner 进程 |
| 开发环境 | 用户操作的隔离空间；Firecracker 模式下每个环境对应独立虚拟机与磁盘 |
| runtime | 复用的 standalone 程序，承载用户连接、终端、文件和 AI 任务通道 |
| 虚拟机管理服务 | 本方案新增的小型服务，响应 Runner 的有限管理请求；不是可信安全边界 |
| 系统盘模板 | Runner 按不可变版本组合生成的共享只读源文件，仅用于复制，不直接给用户环境写入 |
| 存储池 | 以真实承载文件系统为边界管理的空间；不是目录名称，不要求 LVM |
| 保护锁定 | 磁盘压力等故障触发后，持久阻止环境再次运行的安全状态，不等同于用户停止目标 |

```text
中心服务
├─ 用户／分组授权、Runner 配置、环境规格与目标、计费
├─ 镜像仓库、固定组件与 runtime 分发
└─ 设备授权与既有中转
         │ 签名控制同步；Runner 主动连接
         ▼
Runner
├─ 能力预检、安装状态、驱动分派、状态日志
├─ 镜像缓存与转换器、磁盘管理、网络与资源限制
├─ 本地磁盘压力保护
├─ gVisor 驱动 → 既有 Docker/gVisor 环境
└─ Firecracker 驱动
   ├─ jailer + Firecracker API → 虚拟机生命周期
   └─ vsock → 虚拟机管理服务
               ├─ init + 挂载／网络初始化
               ├─ 普通用户 runtime → 既有中转
               └─ 用户项目与工具，可在虚拟机内 sudo
```

安全决策由中心服务和 Runner 执行。虚拟机内 root 可修改管理服务、runtime 和状态文件，因此其报告只能作为操作反馈，不能单独证明身份、归属、资源限额或已安全停止。

| `engine/internal/driver` | Docker exec 编排及临时 gVisor 容器准备 runtime | 保留原驱动，增加 Firecracker 和独立的安全 runtime 准备路径 |

首版不应为了运行 Firecracker 而强制依赖可用的 gVisor。共享镜像格式不等于依赖 Docker daemon；纯 Firecracker 路径的镜像读取、转换和 runtime 准备必须能够独立完成。

## 4. 统一宿主安装器

### 4.1 选择规则

首次安装默认 `auto`。`auto` 是安装选择策略，不是某个环境的实际驱动；保存到环境中的值必须是 `firecracker` 或 `gvisor`。

```text
同一条接入命令
  → 验证平台、身份绑定参数和中心服务协议兼容性
  → 共用条件检查
  → Firecracker 能力检测
      ├─ 明确可用 → 下载固定组件 → 受限启动自检 → 选择 Firecracker
      └─ 明确不支持 → Docker/gVisor 组件准备与自检 → 选择 gVisor
  → 持久保存选择、版本和原因
  → 注册／复用 Runner 身份、上报能力
  → 启动服务并核对健康
```

中心服务下载协议若要求先注册，可以提前建立身份，但在全部检查完成前保持未就绪、不可调度；不为文档中的步骤顺序增加匿名下载或放宽现有鉴权。

| 情况 | 行为 |
| --- | --- |
| 两种都可用 | 默认 Firecracker |
| `/dev/kvm` 不可用或实际平台不支持所选 Firecracker | 明确说明原因，尝试 gVisor 自检 |
| 共用条件不满足 | 报错，不通过切换驱动掩盖空间、cgroup 等问题 |
| 组件尚未安装 | 正常下载与准备，不视为硬件不支持 |
| 下载／证书／摘要／磁盘错误 | 明确失败并允许重试，不静默回退 |
| Firecracker 自检明确判定平台不兼容 | 确认清理完成后可尝试 gVisor |
| 自检超时、未知崩溃或残留无法清理 | 报错，不随意归类为平台不支持 |
| 两种都不满足 | 报告安装未就绪，禁止调度，不降级为普通 runc 容器 |

安装成功、Runner 在线、驱动就绪、管理员启用调度、用户获得访问授权是不同条件。安装器不能自动向全部用户开放新机器。

### 4.2 能力检测

共用检查：Linux 与架构、现有 systemd 管理方式、实际服务权限、cgroup v2 所需控制器、数据目录归属、可用字节与 inode、网络管理能力、中心服务与发行兼容性。保留现有系统依赖要求；新增工具随固定发行物提供或明确预检缺失，不偷偷调用公网包管理器。

Firecracker 检查在拟使用的服务权限下执行：

- 实际打开 `/dev/kvm` 并核对 KVM API、必要扩展、创建 VM／vCPU 能力；不只检查文件存在或 CPU 标志。[R1][R2]
- 核对所选 Firecracker、jailer、宿主内核、架构与页大小组合；不根据云厂商或实例名称推断嵌套虚拟化可用。
- 组件准备后启动受限、短时测试虚拟机，验证内核启动、块设备读写、vsock、jailer、TAP 和专用网络规则的建立／清理。
- 测试实例无用户数据、用户身份与真实账单；使用固定校验的最小测试材料，不提前转换真实开发环境镜像。
- 自检组件和 Runner 共用同一能力检查逻辑；安装自检不代表完整 AI 工作负载与安全验收通过。

gVisor 回退沿用现有 systrap 配置，核对 Docker API、专用 runsc、实际 cgroup、网络与测试容器启动／退出。缺少 KVM 不意味着 gVisor 自动就绪；上游平台说明支持在无虚拟化能力的场景采用 systrap，但项目仍需验证自己的固定版本。[R10]

所有探测资源使用独立标识、限额和超时，失败也必须回收。安装器不得为了成功而格式化现有磁盘、修改内核启动参数、禁用安全策略或重启宿主服务器。

### 4.3 修复、升级与驱动保存

首次成功选择后保存默认引擎。重装、同版本修复和普通升级保留默认值、身份、数据目录与环境绑定；不得发现 KVM 后自动迁移原 gVisor 环境。

管理员可通过明确管理操作启用新驱动并调整“后续新环境”的默认值；已有环境仍按原驱动运行。不能卸载仍有运行、停止或待清理环境引用的组件。Firecracker 后续失效时不把同一环境改为 gVisor。

安装输出和管理界面应显示实际默认引擎、版本、能力结果、回退原因与可修复错误。纯 Firecracker 新装不强制配置 Docker；若已有 Docker 或旧 gVisor 环境，不重启、卸载或覆盖其业务配置。

## 5. 发行、镜像和组件版本

### 5.1 发布与分发职责

发布阶段只准备 Runner／installer、Firecracker／jailer、Linux 内核、启动配置、管理服务、转换工具、最小自检材料及清单。开发环境系统盘仍由 Runner 第一次使用时转换。

中心服务提供固定镜像和组件，在线／离线安装包均覆盖实际承诺的架构。Runner 只连接配置的中心服务，不回源 GitHub、OSS 或系统软件仓库。已有短期只读镜像凭据与 Runner 身份绑定，禁止跨源转发；二进制 SHA-256 必须来自可信发行清单，不能把同源可篡改的摘要当作独立签名。

发行清单至少描述：架构、组件名称／版本／大小／摘要、镜像适配版本、内核及启动契约、管理协议、转换器版本和最低控制协议。版本号与协议号待实施时分配，不预造“已经支持”的版本。

### 5.2 冻结环境版本

中心服务创建环境时冻结所选架构的 OCI manifest 摘要和相关组件版本，不仅固定可读标签或多架构索引。模板缓存键建议为以下规范化内容的摘要：

```text
架构 + 所选架构OCI manifest摘要 + 镜像适配契约
+ 转换器版本 + 系统盘逻辑容量/文件系统参数
+ 内核摘要 + 启动组件摘要 + 管理服务/协议版本
+ 模板内自带runtime发行摘要（如有）
```

以上是缓存键工程建议，具体清单待锁定。不同 Runner 的同键模板应满足同一内容契约，但不假设生成的 ext4 镜像因时间戳、UUID 等原因必然逐字节一致；每份生成产物另存实际摘要和收据。

默认镜像切换只影响后续新建。既有系统盘不覆盖；runtime 更新独立执行。内核和管理组件升级需要兼容校验与明确维护操作，不能每次启动自动跟随最新版本。

## 6. Runner 首次镜像转换

### 6.1 镜像契约

首版只支持平台维护、适配过的镜像和同架构运行，不做任意镜像转换或跨架构模拟。沿用现有 Dockerfile 中的开发工具，补充平台受控的 init／启动材料；不在 Runner 上执行镜像安装脚本或编译内核。

| OCI 内容 | 转换策略 |
| --- | --- |
| 文件层 | 按规范顺序应用 whiteout、目录替换、所有者、权限及所需 xattr；不是直接叠加 tar [R3] |
| `ENTRYPOINT`／`CMD` | 不直接当作虚拟机 init；使用平台固定启动流程 |
| `USER` | 平台固定普通用户身份，sudo 按 Firecracker 规则配置 |
| `ENV`／`WORKDIR` | 只继承适配契约认可的项，固定 HOME、PATH 和 runtime 状态路径；拒绝控制面凭据注入 |
| `VOLUME` | 不自动挂载宿主目录或创建匿名卷；不符合平台契约的镜像拒绝 |
| `HEALTHCHECK`／`EXPOSE` | 不自动执行或开放端口；平台定义健康检查与网络入口 |
| 身份文件 | 模板不携带设备私钥、用户令牌、共享 machine-id／主机密钥或固定密码 |

运行配置与层文件是不同结构，不能宣称复制文件就完整继承 Docker 语义。[R3]

### 6.2 转换事务

1. 检查本地同键模板；校验清单、就绪标记与完整性，损坏模板隔离后重建，不继续使用。
2. 取得模板键的跨进程锁；重复请求等待同一转换，不重复分配大块临时空间。
3. 原子登记转换工作量预算；检查存储池压力及解包大小、inode／文件数、层数和时间限制。
4. 从中心服务拉取固定摘要的 OCI 对象到受限缓存，校验配置、压缩层和解包契约；不依据镜像自报大小无限解包。
5. 在独立暂存区还原文件系统，防止路径穿越、符号／硬链接逃逸和恶意设备节点；不得挂载用户目录、宿主根目录或 Docker socket。
6. 注入受控启动与管理组件，准备基础用户和固定路径；使用发行版 init，不自研完整 PID 1。
7. 用受控工具把文件树写入稀疏 raw/ext4 模板，禁止执行镜像里的程序作为宿主命令；具体工具链须做隔离、权限和稀疏行为验收。
8. 在一次性副本中做必要启动校验，不能启动共享模板写入身份或运行状态。
9. 完整校验后写入产物摘要及收据，文件与目录同步落盘，再原子发布 ready 标记；发布前不可被环境认领。
10. 清理临时资源并释放预算。中断重试只处理归属明确、无活跃持有者的产物；清理失败显式告警。

普通模板转换与环境创建受并发限额约束。单个环境取消时只释放该请求引用，不随意杀死仍被其他请求等待的共享转换；最后引用消失后的取消策略必须幂等。

### 6.3 模板缓存

模板只读、预算有界、使用受保护引用与 LRU 回收。引用包括进行中的复制／转换和需要保留的发行回滚依赖；环境自身磁盘不是缓存，不能被 LRU 清理。缓存淘汰后新建可重新转换，既有独立磁盘不因模板被删而丢失。

reflink 共享块下，删除模板未必立即释放等量空间；回收成功以真实文件系统可用空间变化为准。不能用逐文件占用简单求和代替存储池剩余量。

## 7. 磁盘布局与持久化

### 7.1 单盘与总容量

每环境只有一块独立可写环境盘，统一保存根文件系统、软件、项目、用户目录及 runtime 身份／状态。管理员只设置磁盘总容量，创建时冻结；首版不做在线扩缩容或宿主自动分区。修改默认规格只影响新环境。该能力尚未上线，直接移除双盘规格，不实现兼容或在线合盘。

| 存储 | 用途 | 写入者 |
| --- | --- | --- |
| 根盘模板 | 公用基础系统内容 | 仅转换器生成与校验阶段 |
| 环境磁盘 | 根文件系统、软件、项目、用户目录和 runtime 身份／状态 | 对应虚拟机 |
| `/tmp`、`/run` 等 | 临时内容 | 对应虚拟机；不承诺重启保留 |

`/workspace`、`/home/monkey`、`/var/lib/monkeyai`及其状态目录位于同一个持久根文件系统，共同受磁盘总容量约束；不再创建第二块盘或额外绑定挂载。实际可用空间需扣除文件系统元数据开销。

首次初始化设置正确UID/GID；管理服务核对根文件系统可写、类型和目录设备一致性。根盘或持久目录异常时中止runtime，不能在临时存储中初始化另一套身份。

### 7.2 环境磁盘创建与归属

创建前先登记环境、磁盘ID、总容量、文件归属与初始化状态。环境盘从只读模板独立克隆，reflink优先，退回普通复制时必须保留稀疏性质并核查空间预算。共享模板不做硬链接可写复用。

完成磁盘初始化后设置环境独立文件系统标识和系统身份；具体 UUID／machine-id 初始化方法纳入启动契约，不能让所有环境共享身份。通过可信本地元数据标识已初始化状态；磁盘丢失、元数据损坏或归属不明均不能自动格式化“修复”。

用户不能提交任意宿主路径、已有盘路径、Firecracker 参数或挂载目标。Runner 通过受控 ID 解析路径，拒绝路径穿越和符号链接替换。虚拟机运行时不在宿主上挂载其可写文件系统，也不在另一虚拟机同时写入。

持久盘必须明确配置并验证 flush 语义：工程方案采用支持虚拟机 flush 的 `cache_type=Writeback`，不能沿用忽略 flush 的 `Unsafe` 默认值；Sync／Async 是 I/O 执行方式，不等于是否同步到稳定存储。[R11] 正常关机后核对底层写入完成；强制终止不保证应用缓冲区里的数据已落盘，也不能承诺消除硬件故障或断电损失。

### 7.3 删除、保留与销毁

停止保留环境磁盘。删除环境撤销访问并确认进程、网络、句柄及设备引用清理，磁盘转入“保留数据”；不把删除等同永久销毁。

保留数据需要可查询的所有者、原环境、Runner、磁盘容量／占用估计、保留原因和时间。永久销毁使用独立授权和明确确认，先核查无运行引用，再清理环境盘与元数据；重复请求幂等。具体 API、确认交互和授权角色在实施前确定。

环境数量沿用“未确认删除仍占名额”的规则，停止不会释放名额；确认删除可释放环境名额，但保留磁盘继续占用存储账，不得借删除反复绕过存储限制。建议增加有保留盘时的Runner退役／卸载校验，避免丢失数据归属；具体清理或交接流程另行确认，不直接复用旧的“没有活跃环境即可遗忘宿主”判断。

只有真实释放后才减少实际占用；文件已 unlink 但仍有打开句柄时不能宣告物理空间已回收。首版不自动到期删除，不承诺一键恢复已删除环境；恢复接口和数据导出不作为已实现能力宣传。

磁盘持久化不等于备份或主机故障容灾。备份建议仅在确认停止后复制环境盘和可信元数据；运行中裸复制不能承诺一致性，首版不实现备份系统。

## 8. 设计不变量

以下不变量同时约束后续协议、代码和测试：

1. 环境驱动、磁盘绑定和身份归属不能因安装器重跑或启动失败而静默改变。
2. 模板永不承载用户写入或用户身份；环境盘永不进入缓存自动清理集合。
3. 同一块可写磁盘不能被两个活跃实例持有；失联、进程 PID 或文件存在均不是可靠的单写证明。
4. 本地保护锁定优先于旧的运行目标；重复同步不得自动重新启动刚被保护停下的环境。
5. 暂停、停止、删除、销毁数据是不同状态；不能用暂停伪造停止和空间释放。
6. 未确认进程退出、资源归属或清理结果时不能报告已停止／已删除。
7. 磁盘超卖允许容量总额超过物理池，但不得宣传所有用户随时写满的保证。
8. 新设计与历史已上线逻辑分开；新增字段、迁移、计费分支和自动恢复政策不能凭文档描述视为已授权上线。

## 9. 磁盘超卖与本地压力保护

### 9.1 逻辑容量与物理空间分账

逻辑容量是用户盘的可寻址上限，不是独占物理承诺。磁盘总逻辑容量允许超过物理池，但必须同时满足两类准入条件：

```text
逻辑准入：现有计入容量的磁盘逻辑总额 + 新磁盘逻辑容量
          ≤ 管理员设定的逻辑超卖上限

物理准入：池当前可用空间 - 在途任务尚未兑现的空间预算
          ≥ 新任务最坏准备空间预算 + 安全余量
```

逻辑账包含运行、停止和删除后保留的环境盘；共享模板／缓存不重复算作用户逻辑承诺，但其物理占用必须纳入池预算。既有磁盘使调整后的上限超标时，只阻止新增，不自动清理数据。

物理账按实际文件系统可用空间及 inode 计算，不能只统计镜像目录，更不能简单相加 reflink 文件的 `st_blocks` 当作精确独占占用。显示单环境占用时注明估计与共享块语义。检查下层配额、thin backing 或对象存储挂载是否改变可用空间保证；首版只支持完成验证的本地文件系统组合。

同一存储池的准入和在途预算更新必须原子化，避免并发转换各自都看到“空间够”。预算记录与任务绑定，重启后通过真实文件和任务状态核对；已体现到文件系统占用的部分不得再次扣作未兑现预算。

### 9.2 安全余量与限速

保护余量不直接拍固定百分比，应至少覆盖：

```text
安全余量 ≥ 受控总分配速率 ×（检测间隔 + 最坏处置时间）
           + 突发／在途I/O预算 + 脏页落盘预算
           + 文件系统元数据／写放大预算 + 控制状态维护余量
```

这是预算模型，不是数学安全保证：必须考虑稀疏分配粒度、COW、不可控的同池业务及错误处理时延。环境盘、转换、复制、日志和缓存下载都纳入控制；只给虚拟机限速却允许转换进程无限写入不合格。

利用固定版本支持的块设备限速与外层资源控制，分别保护每环境及整个池。[R6] 首版优先建议使用专用环境数据文件系统，并把 Runner 身份／控制日志放在不会被用户盘挤满的位置；这是部署建议，不自动为管理员分区。共享系统盘部署必须明确更弱的风险边界并验收。

### 9.3 压力状态机

以下状态名为拟议协议字段，当前代码未实现。恢复阈值必须高于触发阈值，并设置稳定观察窗口避免反复启停。

| 状态 | 新建／启动／转换 | 对已有环境的行为 |
| --- | --- | --- |
| `normal` | 通过双重准入后允许 | 常态限速与监测 |
| `warning` | 仍须通过准入，降低准备并发 | 管理端提示空间和增长趋势 |
| `restricted` | 拒绝新增写入负载；停止／删除控制操作仍可执行 | 只回收可安全回收的缓存，要求运维扩容或清理 |
| `emergency` | 全部阻断 | 本地触发保护锁定，自动暂停／停止受影响环境 |
| `recovery_hold` | 池恢复不等于环境自动恢复 | 保留保护原因，等待明确恢复操作及重新准入 |

用户已授权紧急自动暂停／停止，但没有授权自动销毁数据或空间恢复后自动启动。本设计建议首版保守采用“稳定恢复后，由用户或管理员显式恢复”，不增加自动运行政策。

### 9.4 紧急处置顺序

1. 先锁住池的新写入准入，暂停新转换／下载／复制；保护循环独立于普通环境任务队列，不因长时间转换被阻塞。
2. 持久写入保护事件与环境锁定，包含池、原因、序号、对应代次和时间。记录失败不能当作安全正常；阻断新任务并执行最小必要保护，依赖预留控制空间恢复可追溯状态。
3. 根据池内当前活跃写入者实施限速与保护。初步建议先处理增长快且仍有写入的本系统 Firecracker 环境；若保护窗口不足，则扩大到同池相关环境，不能承诺只影响“肇事者”。具体排序是实施前待确认项。
4. 有充分落盘余量时请求正常关机；危险程度不允许继续增长时先暂停虚拟机执行，再验证写入是否确实收敛，必要时终止对应进程。使用所选版本正式支持的暂停接口，不把暂停当成内存快照或磁盘快照。[R9]
5. 暂停不等于 I/O 已排空、脏页已落盘或存储已释放。对已提交 I/O、后台日志与宿主写回预留空间；不得把一次暂停 API 成功作为停止写入的充分证明。需要正常关机时先确认有安全预算再受控继续运行；不能对已暂停的虚拟机发送关机请求后无限等待。
6. API 不响应或过程超时，依据已核验归属的 PID／启动身份／cgroup 终止进程，不按不可信 PID 文件杀进程；确实退出、句柄和 cgroup 清理完成后上报 `stopped`。未确认则保持失败／未知，不伪造结果。
7. 不保存内存快照，不因保护压力写入更大的内存镜像；不删除环境磁盘。停止只阻止后续增长，并不会自动释放已有占用。
8. 中心服务在线时同步原因并撤销可连接状态；离线也执行本地保护，事件持久后重传。中心服务恢复时按事件序号去重，不覆盖更新的用户操作。

本项授权只覆盖本系统管理的相关环境，不授权停止服务器上不属于本系统的进程、普通 Docker 业务或删除其文件。同池 gVisor／外部业务是否纳入写入保护必须有明确能力与授权；未控制的共同写入者意味着不能承诺完整物理空间安全。

保护控制必须由服务管理器监督并在 Runner 重启后恢复锁定。若监控器退出，停止新调度并报告异常；现有进程在检测恢复前的窗口需要纳入压力测试，不能宣称软件保护能够消除所有宿主故障。

### 9.5 解除保护与空间回收

中心服务的旧 `desired=running` 和同代次重试不得绕过保护锁定。解除要求真实空间稳定恢复、用户仍获授权且余额／数量条件满足，并收到更高代次、明确关联保护事件的恢复操作。首版不默认自动恢复。

模板／失败临时产物只在无持有者、归属可确认时清理；不全局 prune、不删保留用户盘。用户删文件不保证 raw 立即缩小。当前查阅的上游 DISCARD 默认关闭、仅支持可写 Sync virtio-blk，普通文件后端以打洞释放；这不代表项目所选版本已经具有该能力。[R7]

若选择支持的版本，须验证 ext4 → virtio DISCARD → Firecracker → 宿主文件系统的完整链路，以及与 reflink、碎片化、限速和失败恢复的交互。未验证前不提前把预期回收计入余额；不能在宿主对不明已用块随意打洞。

底层文件 I/O 失败可被 Firecracker 映射为虚拟磁盘 IOERR。[R8] 宿主空间耗尽不是普通的虚拟机内 `ENOSPC`；可能影响同池多个环境，因此必须在耗尽之前介入，且保留异常关机与文件系统损坏风险说明。

## 10. 虚拟机管理服务与 runtime

### 10.1 vsock 通道

Firecracker 提供宿主 Unix socket 与虚拟机 AF_VSOCK 的桥接；本方案使用 Runner 发起的连接，不另开 TCP／SSH 管理端口。[R4]

每环境独立管理 socket、受限目录权限和连接归属。拟议协议只含以下操作：握手／状态、设备登录初始化、启动／停止 runtime、准备／切换已指定 runtime 版本和请求关机。拒绝任意宿主命令、任意宿主路径、通用挂载与任意端口代理。

请求绑定环境 ID、实例绑定 ID、本次启动标识、控制代次、请求 ID 和协议版本；响应有大小、时间和并发上限，重复请求幂等。不得因虚拟机返回另一个用户 ID、machine ID 或任意命令而改变中心服务预先绑定的身份／作用域。

可使用本次启动随机量降低错连与重放风险，但虚拟机内 root 能读取本环境秘密，不能把它当成可信远程证明。Runner 不开放可被虚拟机任意调用的反向宿主服务；vsock 服务自身必须按不可信输入解析。

### 10.2 初始化和可用条件

1. init建立必要系统挂载与网络，确认持久根盘和用户目录就绪。
2. 管理服务启动，Runner 核对固定组件和管理协议组合。
3. 以普通用户调用原 standalone `status`／设备码登录；身份私钥只保存在该环境的持久磁盘。
4. 设备申请沿用现有签名控制交换，由中心服务核对用户、Runner、环境、实例和代次；不把设备码写进日志。
5. 登录后核对已有公开身份，再启动 runtime；用户终端、文件和 AI 任务继续使用现有连接票据与中转。
6. 当前代次运行观察新鲜、身份绑定有效且 runtime 的既有连接条件满足，环境才是可连接、可完成创建的状态。

管理服务运行、vsock 可连接或虚拟机 PID 存在均不等于 runtime 已可用。root 修改运行组件导致启动失败，应如实报错，不对可写系统盘自动重置。

### 10.3 runtime 更新独立于系统盘

保留官方固定版本及摘要分发方式，禁止在宿主直接执行环境内或用户提供的二进制来获取版本。现有“临时 gVisor 容器准备 runtime”的路径需按驱动拆分。

工程建议：Firecracker 使用无用户盘、无外网、受限的一次性维护虚拟机验证官方 bundle／释放配套引擎；可以复用发行中的受控维护材料，但不能预生成并代替用户首次转换的开发环境系统盘。维护材料需包含必要依赖并固定版本，具体实现须经过双架构原生测试。

经校验的版本在目标环境的维护流程中暂存、验证、原子切换并保留前一版本。更新期间不能启动用户 runtime、签发用户连接或算作已可用；需要启动虚拟机进行维护时，必须明确上报维护阶段，而非假报物理停止。

管理服务的成功回复不是中心服务的全部依据：以中心服务冻结的版本和后续 runtime 身份／连接验证完成更新，且不承诺防止有 root 的用户事后修改自己的程序。失败保留原程序与磁盘，报告当前真实状态，不通过重建根盘回滚用户环境。

## 11. 生命周期、代次与重启恢复

### 11.1 标识划分

- `environment_id`：用户长期持有的开发环境。
- 既有 `instance_id`：持久实例／磁盘绑定身份，沿用当前持久 gVisor 模式的稳定绑定思路，不拿进程 PID 替代。
- `generation`：中心服务目标与操作代次，旧代次不能覆盖新代次。
- 本次启动标识：每次创建 Firecracker 进程生成，用于拒绝上次启动遗留的状态、socket 和管理回复。
- 保护事件序号：Runner 本地持久事件序列，与中心服务目标代次分开；不得擅自伪造中心服务的新目标。

字段名与协议版本属于拟议接口，需与现有服务实现统一。

### 11.2 状态与动作

| 动作 | 状态／执行顺序 | 完成条件 |
| --- | --- | --- |
| 创建 | pending → preparing → starting → running | 磁盘与隔离就绪、runtime 实际可连接 |
| 正常停止 | stopping → stopped | 先禁止新连接，正常关机优先；进程退出和资源清理确认 |
| 再次启动 | preparing → starting → running | 原盘归属有效、无保护锁定、通过新代次与准入 |
| 保护暂停 | protection=latched，observed=paused | 确认暂停并继续控制在途写入；不释放内存或环境名额 |
| 保护停止 | protection=latched，observed=stopped | 确认退出，保留数据，禁止被旧运行目标拉起 |
| 删除环境 | deleting → deleted，data=retained | 访问撤销、执行资源确认回收、磁盘进入保留记录 |
| 永久销毁 | 独立销毁操作 | 授权确认、无引用、物理清理成功及可审计收据 |
| 未知／失败 | failed 或 stale，并保留真实观察信息 | 不自行当作停止，不自动换机器或换驱动 |

`paused`、维护阶段和数据保留状态需显式扩展或独立表达，不能强塞进现有 `running/stopped` 造成计费或调度误判。未经协议升级的客户端至少显示不可连接及可读原因，不伪造支持全部新操作。

### 11.3 幂等与单写

沿用每环境跨进程锁、目标指纹、先落盘后上报和结果重传。相同代次同规格重试认领现有归属；同代次不同规格拒绝；更高代次取消旧准备任务，确认其退出后清理。

Runner 重启时核对进程可执行文件、启动时间／身份、API socket、cgroup、磁盘 inode 与环境记录，不能仅按 PID 认领。虚拟机进程运行归属需由服务管理结构保障，Runner 正常重启不应连带误杀现有环境；具体 systemd 单元／scope 分离方式属于实现验证项。

所有未完成操作有阶段日志与恢复入口，删除／停止可以重试但不能重复格式化。磁盘文件缺失、身份不符、锁被其他实例持有或进程归属不明时锁定并报错。

服务器重启不承诺恢复进程内存；用户环境是否重新运行不能仅由 init/systemd 自动拉起。首版按安全保守原则先核对控制目标、最近操作和保护锁定；异常退出后的重新启动仍需显式操作，不因周期同步重复执行用户命令。

## 12. 网络与外层安全

### 12.1 网络拓扑

工程建议每环境使用独立网络命名空间、TAP 和受控到宿主的 veth／路由连接，由 Runner 分配冲突检查过的私有地址并配置 NAT／防火墙。Firecracker 网络不复用 Docker bridge 作为不可见硬依赖。

创建前检查现有接口、路由与保留地址，地址分配持久且并发安全；不要求用户提交 TAP 名称或网段。所有 nftables 规则使用专用表／链和归属标识，不 flush 全局规则，也不覆盖已有 Docker 业务网络。

`public-only` 沿用既有允许的公网端口与 DNS 策略，默认拒绝宿主地址、未授权私网、云元数据、跨环境流量及内网绕行。中心服务位于私网时使用管理员明确配置的最小地址／端口例外，不放行整个网段。按 TAP／命名空间绑定来源，防止虚拟机 root 修改 IP／MAC 绕过隔离。

首版若未完整实现 IPv6 策略，就在虚拟机外阻断 IPv6，不能仅在虚拟机内关闭。使用受控 DNS，防止解析到内网地址后绕过出口规则；规则以实际目标地址和网络路径执行，不能只验证域名字符串。

`isolated` 不可用于必须连接中心服务的托管 runtime。用户预览和入站继续走既有受控中转，不自动把 `EXPOSE` 转成宿主端口映射。

### 12.2 资源与安全边界

Firecracker 与 jailer 必须匹配版本，保留默认 seccomp，隔离 socket／磁盘访问，确保 Firecracker 以受限宿主身份运行；具体 jailer cgroup 参数必须验证实际归属，不以“命令执行成功”代替限制生效。[R5]

- 配置虚拟机 vCPU 数与内存，同时设置外层 CPU、内存、PID、文件描述符、I/O 和日志边界。
- 外层内存预算包含虚拟机内存及 VMM／辅助进程开销，不能直接等于用户内存而触发非预期 OOM；开销实测后固定到规格规则，不另向用户偷偷加价。
- 现有 CPU 规格使用 millicpu，而虚拟机配置需要整数 vCPU。首版支持的粒度、取整映射与外层 quota 必须明确，不隐式截断；不修改既有 gVisor 规格。
- 宿主 `pids.max` 限制 VMM／辅助进程，不宣称等于虚拟机内的进程数上限。允许 sudo 后虚拟机内任务限制不是对用户不可绕过的安全边界。
- 拟保持现有单环境资源限额及数量准入；CPU／内存总规格超卖口径不因磁盘方案悄悄改变。物理内存和 VMM 开销不足时仍须拒绝启动，不能将账面超卖当作可运行保证。
- 串口输出、Firecracker 日志、转换日志都使用有界缓冲／轮转，禁止用户控制的输出耗尽磁盘；这一点也属于 Firecracker 官方生产要求。[R5]

不暴露宿主 Docker socket、任意 hostPath、宿主设备、Runner 私钥或管理员凭据。用户可控制虚拟机内 root 不代表其能控制宿主；但 Firecracker 也不替代宿主补丁、微码更新和运行时安全维护。

## 13. 中心服务、数据模型与协议演进

以下为逻辑字段设计，具体表名／接口以实施时的现有结构为准，避免为了模型整齐重建已有控制面。

| 对象 | 必须表达的新增内容 |
| --- | --- |
| Runner 配置／能力 | 已保存默认驱动；分驱动支持、安装、就绪、版本与原因；协议版本及检测时间 |
| 环境冻结规格 | 实际驱动、架构、镜像与组件摘要、磁盘逻辑容量、磁盘绑定、管理协议 |
| 本地／远端观察 | 启动标识、观察代次、runtime 状态、停止原因、维护／保护状态与事件序号 |
| 存储池状态 | 实际可用字节／inode、池标识、逻辑额度、在途预算、压力状态、更新时间 |
| 保留数据 | 所有者、原环境、Runner、两块盘 ID 与容量、保留原因、销毁状态与审计 |
| 操作记录 | 幂等键、代次、请求者、来源、阶段、错误类别、保护／销毁关联事件 |

中心服务不接收用户任意宿主路径或 Firecracker API 配置，只保存受控规格。检查用户授权、数量、余额、驱动就绪、存储准入及所需能力；Firecracker-only 的 sudo 等能力不能在回退时当作 gVisor 也具备。

已有 gVisor 环境按其原语义回填驱动；新增存储字段不使旧目录持久化自动变成 raw。新组件和默认策略只对新建适用，不做原地跨驱动迁移。

数据库使用下一可用增量迁移，不重写已经存在的 `000040_cloud_environments` 或重放旧开发迁移。旧版本有未知驱动／保护状态／保留盘数据时不得强制回滚或丢弃记录；先确认停止、数据保留和兼容接管条件。新增协议由中心服务先兼容，再升级 installer／Runner，最后显式启用新驱动。

中心服务未知新协议时拒绝调度 Firecracker；Runner 不谎报 gVisor。能力上报包含观测时间，过期结果不得继续当作就绪。注册身份、签名交换、代次校验和既有访问范围继续复用。

## 14. 计费与保护事件衔接

### 14.1 不改变的规则

同规格 gVisor／Firecracker 同价，按分配 CPU、内存与可确认运行秒数计量，每分钟结算；模型／工具费用分项；存储暂不收费。默认收费开关和价格仍由管理员控制。

转换、安装自检、维护及创建尚未可用的阶段不启动环境计算计费。环境初次真正可用后开始；关闭客户端或空闲不停止收费。正常停止以中心服务确认停止为结束点，保留原尾费和未知失联区间不补扣规则，不重新定义账单历史。

余额耗尽通过中心服务禁止新建／启动并发起停止，数据保留。磁盘本地保护是独立安全机制，不代表已经实现失联时的本地资金租约。

### 14.2 新增保护性暂停是上线阻断项

暂停不等于停止，也不等于释放资源；不能直接用现有“确认停止结算”分支处理。用户已确认：平台磁盘压力导致的保护暂停期间不收计算费，显式恢复并重新可用后再开始计费。该规则需要独立保护事件和计费时段支持，目前尚未接入生产账务。

上线前必须明确：暂停计费起止、Runner 离线事件的时间可信边界、迟到事件与已结算流水的处理、维护阶段的识别，以及保护停止／用户停止的并发优先级。事件必须绑定既有时段、环境和序号，重复上报不能重复扣费或退款；若需调整已结算金额，通过现有不可变账务补偿机制，不改历史流水。

未完成上述事件与账务衔接的实现和验证前，不启用会把暂停环境持续当作可用收费的生产路径，也不能通过“客户端断开即免计费”破坏原有空闲收费政策。

## 15. 故障处理矩阵

| 场景 | 必须行为 |
| --- | --- |
| Firecracker 平台不支持 | 初次安装可回退验证后的 gVisor，显示原因 |
| 组件损坏／下载失败 | 失败重试，不把供应链错误伪装成硬件不支持 |
| 转换中断 | 半成品不可见，重启核对任务后安全清理／重试 |
| 同镜像并发创建 | 同键转换去重；预算原子登记，环境盘仍各自独立 |
| 创建时空间不足 | 保留既有环境，拒绝新任务，不预造运行成功 |
| 运行中空间危险 | 本地锁定＋保护性暂停／停止；不删数据，不等中心服务批准 |
| 用户盘逻辑容量耗尽 | 报告该盘容量问题，不自动扩大文件或全池放开准入 |
| 根盘或持久目录未就绪 | 不启动runtime，不在临时存储初始化新身份 |
| 磁盘丢失／归属不明 | 锁定失败，不重建空系统盘冒充恢复 |
| 管理服务被 root 改坏 | 报错；外层停止和限额仍有效，不自动覆盖用户系统 |
| runtime 退出 | 标记不可用，禁止旧代次反复执行；显式恢复 |
| Runner 进程重启 | 恢复阶段日志、保护锁定及预算，核验后认领已存在进程 |
| 宿主服务器重启 | 冷启动规则，核对目标与锁定，不恢复内存或自动迁移 |
| 中心服务失联 | 本地磁盘保护继续；未知区间按既有计费规则处理 |
| 停止失败／API 卡住 | 核验归属后强制结束；无法确认则保留失败状态 |
| 删除成功上报丢失 | 重传幂等结果，不再次销毁保留磁盘 |
| 暂停后收到旧 running 目标 | 保护锁定优先，拒绝自动拉起 |
| 升级后缺 KVM／驱动不可用 | 不切换已有环境驱动，不损坏盘，报告不可用 |
| 清理失败或文件仍有句柄 | 不假报资源回收，保留引用与可重试操作 |

对 fsck 等文件系统修复必须保证虚拟机停止和单写；先记录诊断，不默认执行破坏性修复。不可恢复错误不能以“格式化重试”掩盖。

## 16. 可观测性与操作界面

管理端至少展示：默认驱动及回退原因、每驱动能力／组件版本、磁盘总逻辑容量、池真实余量／inode、超卖总额、压力阶段、最近保护动作、保留数据清单、当前 runtime 实际版本。

环境端至少提供：实际执行方式、可用能力差异、准备阶段进度、停止／暂停原因、数据保留说明与恢复条件。客户端新页面不是本轮默认承诺；接口及现有管理页面必须足以诊断，旧客户端不能把暂停显示为运行正常。

结构化日志使用 Runner／环境／代次／启动标识／操作 ID／模板键关联。不得记录私钥、设备码、Bearer token、完整登录输出或用户文件内容。日志和错误文本有界，不能将用户 root 写入的内容不加处理地作为可信管理消息。

需要度量转换耗时和峰值空间、缓存命中、复制方式、启动至可连接耗时、资源限额、池剩余与增长、保护动作时延和错误、回收实际空间、版本分布。性能指标先记录基线，不编造首版毫秒级启动承诺。

## 17. 工程拆分与交付顺序

本节是整体实施计划，当前进度以[实施记录](firecracker-environment-implementation.md)为准，不代表获准部署。代码实施沿用同一工作树；Pro gitlink、生产发版和真实安装不随本阶段自动变更。

| --- | --- | --- |
| P0 契约与参数 | 选择固定发行／架构／文件系统组合，确定磁盘容量、保护阈值、CPU粒度、暂停计费与恢复接口 | 剩余参数有明确决定，协议／迁移设计可审查；暂停期间免计已确认 |

| P5 集成验收与发布准备 | 受支持双架构原生验收、混合旧环境、故障演练和文档 | 完整验收矩阵通过，产物可追溯；实际部署另行授权 |

实施涉及的主要位置：

- MonkeyCode：`monkeyai/engine/internal/preflight`、`lifecycle`、既有 `driver`、拟新增 Firecracker／镜像转换／存储保护模块、`host` 与 `control`。
- MonkeyCode 中心服务：`monkeyai/backend/internal/environment`、host API／发行接口、增量迁移、既有积分结算与设备授权；只做必要适配，不重写成熟控制面。
- MonkeyCode 管理端：现有宿主与环境页面增加真实引擎／保护／保留数据信息，不重建全套 UI。
- MonkeyCodePro：`pkg/installer/engine`、`pkg/installer/deploy/monkeyai_engine.go`、统一引导脚本、发行清单与打包、开发环境镜像适配材料。
- 现有 standalone runtime 接口优先保持不变；确需变更时单独兼容设计，不把管理服务做成 runtime 的另一套实现。

安装器是首版必交付内容，不因开发顺序排在驱动之后而被推迟到后续版本。
